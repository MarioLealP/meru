# Meru standards

What every Meru repository follows. Written for people and agents alike. Each rule says how it is held: **checked** means a tool fails the build, **review** means a person or agent
reads for it. Anything that can be checked should be, set once in Meru/nuwa-python so new apps inherit it.

An exception is written where it applies, with the reason. A rule without a check will drift.

## Python

- **Python 3.15.** `requires-python = ">=3.15"`. *checked*
- **uv** for packages and environments, `uv.lock` committed and current. *checked*
- **ruff check, ruff format, ty check** all pass, tests included. Settings in `pyproject.toml`, line length 120. *checked*
- **Ruff rules:** `E F W I UP B SIM RUF Q C4 FAST N PT ERA D C901`, `preview = true`, Google docstrings. Ignored: `D107`,
  and in `tests/` `D` and `RUF029`. New code follows this from day one; old code as each app gets its pass. *checked*
- **pydantic or SQLModel for every model.** No dataclasses, NamedTuple or TypedDict. Value objects are frozen, and
  outside data is validated on the way in. *review, can be checked*
- **A class that holds data or dependencies is a frozen pydantic model**: no `__init__`, no work in the constructor.
  Exceptions and Temporal workflow classes are the only ones outside this. *review*
- **Field names are snake_case.** Outside names like `removedAt` come in through `Field(alias=...)`. *checked*
- **pydantic-settings for config.** No python-dotenv, no direct environment reads in app code. *review, can be checked*
- **httpx2 for HTTP.** *review, can be checked*
- **Async code doesn't block.** Reading a small local file, like a mounted token, is fine. *review*
- **No god files, no god functions.** One module, one job. Around 300 lines is the guide; `check.sh` fails a source file
  over 500. Tests are exempt. Function complexity stays within ruff's `C901` default of 10. *checked*
- **Secrets** come from OpenBao through ESO into the environment, and reach code as `SecretStr`. Never in a frontend,
  a repo or a log. *review*

## Data

- **PostgreSQL.** No MongoDB, no other database. *review*
- **Always through the ORM** (SQLModel). No raw SQL in application code. Migrations are autogenerated by Alembic and
  hold the SQL it writes. Triggers, functions and grants the ORM can't express are declared in code with alembic_utils,
  so Alembic tracks them; that is the one place SQL text lives. *review, can be checked*
- **Always async database access:** async engine, async session, async routes. *review*
- **Migrations** with Alembic, reversible, a date prefix and a descriptive name. *review*
- **Explicit names** for indexes and constraints. Tables in lowercase snake_case, singular; time columns end in `_at`
  or `_date`. *review*
- Joins, filters and aggregation happen in the database, not in Python. *review*

## HTTP APIs (FastAPI)

- **Lightweight RFC first:** decently RFC when in doubt, never ceremony. Nouns in paths and the method as the verb; the
  usual RFC 9110 codes (201 + `Location`, 303 after a form POST, 409, 422, 502/503); errors as RFC 9457 problem details.
  Plain `application/json` otherwise: no custom or versioned media types, no HATEOAS, no envelopes. Protocol-named
  paths (OAuth `/callback`, probes) are the only exception to nouns. *review*
- **Every write is idempotent**, in every Meru API: repeating it has the same result as doing it once. Temporal retries,
  browsers double-click, passes run again. A repeat that finds the work done answers success with the current state;
  an error means a real conflict. Use what is naturally there, `PUT` to a known key or a `POST` that checks first, and no
  `Idempotency-Key` stores. Apps moving to Meru get the same pass. *review*
- **`async def` routes for non-blocking work.** Blocking calls go to a threadpool, heavy work to a queue. *review*
- **Dependencies** carry shared checks such as "this record exists" and are chained, not repeated. *review*
- **API docs off** in production unless the API is public. Routes state `response_model`, `status_code` and their
  error `responses`. *review*
- **One router module per resource** in `api/` once an app has more than one; the logic behind it lives in `core/`
  (see Layout). *review*

## Layout

Every app is laid out the same way, by layer, so anyone can find a thing without reading the app first.

- **The top of `src/<app>/` holds only `__init__.py`, `__main__.py` (the entry point) and `config.py`** (settings).
  Everything else lives in a folder. *checked*
- **Fixed folder names**, each used only when the app has that kind of code:
  - `api/` - the FastAPI app, its dependencies, one router module per resource.
  - `clients/` - code that talks to an outside system, one module per system (`gitea.py`, `openbao.py`, `kube.py`,
    `thoth.py`, `temporal.py`, ...). Nothing else calls those systems directly.
  - `models/` - pydantic and SQLModel models used by more than one folder. A model only one module uses stays in
    that module.
  - `core/` - the app's own rules and decisions. Prefer plain functions that take what they need and return a
    result; outside calls go through `clients/`.
  - `db/` - tables, the session, and the alembic_utils objects (triggers, functions, grants).
  - `workflows/` and `activities/` - Temporal apps.
  - **A job with several steps** (a sweep, a purge, a scan, snapshots) gets its own folder named after it
    (`sweep/`, `purge/`), holding its steps.
- **`tests/` mirrors the folders** of `src/<app>/` (`tests/api/`, `tests/core/`, ...); shared fixtures in
  `tests/conftest.py`. *review*
- **A layout pass moves code, it doesn't change it:** same behaviour, imports and entry points updated, every check
  green before and after. *review*
- **Atlas** is several packages in one repo; each package follows this inside. *review*

## Tests

- **pytest, async tests through pytest-asyncio.** *checked*
- **Every test is atomic:** its own data, nothing shared with another test, no reliance on order, so tests could run
  concurrently without stepping on each other. They don't have to. *review*
- **Tests stay fast:** an app's whole suite runs in under 2 minutes, and `check.sh` fails past that. Test what can really
  break, not every line; a suite near the limit gets looked at before it gets workers. *checked*
- **Fake an outside system from a captured real response**, never from what a field is assumed to mean. *review*
- **`dependency_overrides`** to replace FastAPI dependencies, and an async client with `ASGITransport`. *review*
- **No coverage floor**: a percentage pushes tests written for the number. *review*

## Repositories

- **`scripts/check.sh` runs every CI step**, and passes before a PR. *checked*
- **Conventional Commits** for commits and PR titles. *review*
- **Containers** run as a non-root user with a digest-pinned base. *checked by Kyverno*
- **Before pinning a version**, check the real latest release and its advisories. *review*
- **Shared code** lives in one Meru repo that holds actual code only, used as a git submodule pinned per app. Settings
  and project files stay in each app. It holds what is truly the same, and the third copy of the same logic moves
  there. *review*
- **Template drift:** app `ci.yaml` and `check.sh` match Meru/nuwa-python unless the difference says why. *review*
